# Propose a song

The local checker is implemented; public automated intake remains closed until
the repository's trusted CI workflow and maintainer review process are enabled.
Passing the checker means a proposal is eligible for review. It does not merge
anything, publish on ChimePond, create ownership or bypass platform verification,
approval or listing rules.

## One song, three data changes

Each song PR adds one complete original Standard version:

1. `records/<sha256>.tl`: the exact native canonical record.
2. `contributions/<sha256>.json`: its public metadata and declarations.
3. `library.json`: append exactly one matching song at the end of `songs`.

Keep every existing catalog entry and record unchanged. Other additions,
deletions, renames, scripts, workflows, executable files, links and submodules
are refused. The three data files must have Git mode `100644`. Submit another
song as another PR. Downloading and playing a song needs only its `.tl`; neither
JSON file is a playback dependency.

Build the PR as at most 20 single-parent commits directly on the current `main`
commit; merge commits are refused. Merge and rebase merges keep every commit, so
each earlier commit may hold only `main`'s files and the final versions of the
three data files. An earlier draft of the record or a JSON file, or a file added
and later removed, is refused: squash such fixes, and update an outdated branch
by rebasing it instead of merging `main` into it.

Use an explicitly trusted native renderer to prepare and replay your record:

```sh
"$TRUSTED_HARNESS" --play draft.tl --merged complete.tl
"$TRUSTED_HARNESS" --play complete.tl
python3 -c 'import hashlib,sys; print(hashlib.sha256(open(sys.argv[1],"rb").read()).hexdigest())' complete.tl
```

New community records use 44100 or 48000 Hz and contain no more than 1,000,000
bytes of valid UTF-8. Other native instrument sample rates remain valid for
local use. Three independent limits apply:

- Duration: longer than 20 seconds and at most 300 seconds, measured in native
  frames.
- Browser verification memory: the trusted renderer's `--inspect` row reports
  `render_bytes_lower_bound` and `pcm_bytes` (frames × channels × 2). Admission
  needs `render_bytes_lower_bound` ≤ 201,326,592 bytes (192 MiB) and
  `render_bytes_lower_bound` + 3 × `pcm_bytes` ≤ 268,435,456 bytes (256 MiB).
  The lower bound itself grows with the PCM size, so more channels and a higher
  sample rate allow fewer seconds.
- Time: native inspection and native replay each have a 120-second deadline and,
  on POSIX hosts such as the Linux CI runner, a 120-second CPU-time limit. Very
  dense arrangements can reach it before the other limits, and replay speed
  depends on the machine that runs the check.

So 300 seconds is the duration cap, not a promise. For a minimal one-voice
reference draft the longest admissible new song is:

<!-- duration-table: generated by tools/duration_table.py --harness "$TRUSTED_HARNESS"; do not edit by hand -->

| --- | ---: | ---: | ---: |
| `off` | 1 | 300.000 s (duration rule) | 300.000 s (duration rule) |
| `stereo` | 2 | 299.828 s (memory budget) | 275.467 s (memory budget) |
| `binaural` | 2 | 299.708 s (memory budget) | 275.357 s (memory budget) |

| `amb3` | 16 | 37.463 s (memory budget) | 34.419 s (memory budget) |
<!-- end duration-table -->

Voices, events and effects add only a little to the lower bound (64 binaural
voices moving at order 3 add about 0.3 MB at 100 seconds), but they add render
time, so a dense arrangement can reach the time limit first.
`"$TRUSTED_HARNESS" --inspect complete.tl` prints your record's own
`render_bytes_lower_bound` and `pcm_bytes`, and a refusal names the values it
observed.

Native inspection, saved PCM hash, block independence and exact canonical bytes
must all pass. The canonical
SHA-256 is unique across every existing version, regardless of title or author.
Adding comments or whitespace is not a way to create another canonical identity.

A byte identity is not an originality or audio-equivalence test. Renaming streams
can change canonical bytes without changing music; submitting another person's
work with altered names does not satisfy the original-work declaration. When the
rendered PCM hash equals the saved `hash` line of an existing record, an otherwise
eligible proposal stays eligible and names that record for reviewers; other
changes can alter the hash without making the work original. Maintainer review
remains necessary. No automated result establishes the contributor's rights.

other sample rates and arrangements beyond the community verification budget.
Retaining those records does not make them examples of current intake eligibility.

## Metadata and declarations

Copy the following shape, replace the hash and song fields, and retain `null`
for unknown genre, tempo or model. False flags below deliberately do not consent.
Set a declaration to `true` only when the person submitting has accepted it.

```json
{
  "version": 1,
  "record_sha256": "<64 lowercase hexadecimal characters>",
  "song": {
    "id": "your-title-<first 12 hash characters>",
    "title": "Your original title",
    "collection": "Contributions"
  },
  "made_by": "agent",
  "genre": null,
  "tempo": null,
  "model": null,
  "consent": {
    "version": "3",
    "cc0": false,
    "dataset": false,
    "age16": false,
    "history": false,
    "original": false
  }
}
```

All shown fields are required; unknown fields and duplicate JSON members are
refused. The declaration file has the same 1,000,000-byte cap as the TL.

- `song.id` uses lowercase ASCII letters, digits and hyphens and ends with
  `-<first 12 hash characters>`; it must be new. The title has 1–60 characters
  and the collection at most 200. Both are in Unicode NFC form, show at least
  one visible character and neither start nor end with whitespace or a blank
  filler such as U+3164. They contain no control, format, private-use,
  unassigned, surrogate, line-separator or paragraph-separator characters and
  no more than four combining marks in a row. The joiners U+200C and U+200D are
  the exception: either may follow a virama or stand between two letters, as
  Persian and Indic spelling needs, and U+200D may also join two emoji. A
  refusal names the code point. Whether a character is unassigned follows the
  Unicode database of the Python that runs the checker; Python 3.12 has
  Unicode 15.0.
- `made_by` is `agent`, `human` or `mixed`. The catalog entry keeps it in
  `discovery.provenance`, so a merged song keeps its declared author kind.
- `genre` is `null` or a 1–160 character label using letters, digits and
  `._:+/@-`. Choose your own description; the checker does not judge the style.
- `tempo` is `null` or `{"min_bpm":90,"max_bpm":95}`. Values describe quarter-note
  BPM, must be finite and positive, and satisfy `min_bpm <= max_bpm` within the
  existing catalog's safe-number range. This is not a tempo map.
- `model` is `null` or `{"id":"reported-model/version","source":"client-reported"}`.
  Its source is `client-reported` or `user-stated`; its ID uses the same bounded
  label characters as genre. Do not infer a version from a filename or style.

Consent version `3` requires all five exact boolean declarations: you are at
least 16; the composition is original and you hold the rights needed for this
contribution; you dedicate this exact new record under
[CC0 1.0 Universal](https://creativecommons.org/publicdomain/zero/1.0/); you agree
to public research-dataset inclusion; and you accept retained history and copies.
This declaration applies only to this new record. It does not relicense the
retained Apache-2.0 archive or other contributions.

The appended catalog entry copies `song.id`, `title` and `collection` and has
one version:

```json
{
  "id": "your-title-<first 12 hash characters>",
  "title": "Your original title",
  "collection": "Contributions",
  "variants": [
    {
      "kind": "standard",
      "id": "your-title-<first 12 hash characters>/standard",
      "paths": [
        "records/<sha256>.tl"
      ],
      "discovery": {
        "record_sha256": "<sha256>",
        "source": "library.json",
        "provenance": {
          "made_by": "agent"
        }
      }
    }
  ]
}
```

For a declared genre/tempo, add `discovery.metadata` using the existing catalog
shapes: genre is `{"value":"your-label","source":"creator-declared"}`; tempo
copies its range and adds `"source":"creator-declared"`. `discovery.provenance`
always copies `made_by`; for a known model it continues as
`{"made_by":"agent","model":"reported-model/version","model_source":"client-reported"}`
(or `user-stated`). Omit each unknown field; never add editorial `featured` or
`showcase` selections. The checker compares the entry to the declarations.
Retained archive entries carry only the model pair or no provenance, and
`tools/validate.py` accepts both forms.

`library.json` has one accepted byte form: the current file with only this entry
appended, written as Python's `json.dumps(value, indent=2, ensure_ascii=False)`
plus one final newline. That means two-space indentation, non-ASCII characters
as UTF-8 rather than `\u` escapes, LF line ends and no trailing spaces. Keys
follow the order shown: `discovery` holds `record_sha256`, `source`, `metadata`,
`provenance`; `metadata` holds `genre` before `tempo`; a tempo is `min_bpm`,
`max_bpm`, `source`; a genre is `value`, `source`; a provenance is `made_by`,
`model`, `model_source`. Existing entries keep their bytes, including key order. This
rewrites an edited file in that form without changing key order or values:

```sh
python3 -c 'import json; v = json.load(open("library.json", encoding="utf-8")); open("library.json", "w", encoding="utf-8", newline="\n").write(json.dumps(v, indent=2, ensure_ascii=False) + "\n")'
```

## Trusted checking

Use Python 3.10+ on Linux or macOS. Run the checker and its companion
`tools/validate.py` from a trusted base checkout. Build the native renderer from
a separately pinned trusted JotTune Synth checkout outside the candidate repo.
The candidate commit's code, package scripts, build targets and workflows must
never run. Both commit arguments are explicit full lowercase Git commit IDs.

```sh
python3 "$TRUSTED_TUNES/tools/validate.py" --root "$TRUSTED_TUNES"
python3 "$TRUSTED_TUNES/tools/check_pr.py" --repo "$OBJECT_REPO" \
  --base "$TRUSTED_BASE_COMMIT" --head "$CANDIDATE_COMMIT" \
  --harness "$TRUSTED_HARNESS"
```

`OBJECT_REPO` contains the base and fetched candidate objects, including every
commit back to the base (CI fetches 20 commits deep); no candidate checkout is
needed. The checker reads blobs directly, bounds JSON/record/command
output and deadlines, and writes only a temporary native-validation directory.
It validates the complete proposed catalog and record membership directly from
Git objects with the ordinary validator's shared rules. The Linux native child
also has a 256 MiB address-space limit. Both supported POSIX hosts cap temporary
native file output at 1,000,000 bytes. macOS retains those file, inspection, output
and time limits but does not claim an operating-system address-space sandbox.
Native inspection and native replay each have a 120-second deadline, and on
POSIX hosts each also has a 120-second CPU-time limit that the operating system
enforces even if the checker itself stops.
The output has `eligible:true`, `approval:"required"` and observed render facts.
`pcm_duplicate_of` lists existing records whose saved `hash` line equals the
rendered PCM hash, usually none. It is a reviewer warning, never a refusal, and
withdrawn records are not compared because their bytes are no longer in `records/`.
`title_collision` lists existing song IDs whose title equals the proposed title
after NFKC normalization and case folding, with joiners, the combining grapheme
joiner and variation selectors removed, blank fillers read as spaces and runs of
spaces collapsed; it is usually empty. It is also a reviewer warning, never a
refusal, and it does not detect look-alike letters from different scripts.
A nonzero exit refuses the proposal. A refusal names sorted candidate paths (at
most five, then a count), the values it observed, such as the sample rate,
length or render bytes, and the first line of native error output. Quoted
values are JSON strings of at most 200 characters, so hidden characters show as
escapes. A timeout names the command and its limit. Eligibility does not establish originality,
copyright clearance, musical quality or moderation approval.

With `--classify` in place of `--harness`, the checker exits 0 and prints
`{"maintenance": true}` only when no commit in base..head changes song data:
`records/`, `contributions/`, `library.json`, `withdrawn.json` or
`.gitattributes`, compared without regard to case. Any other result, including
a merge commit, a longer chain or an unreadable object, means the full song
check must run.

## Pull request CI — prepared, intake closed

`.github/workflows/tune-pr.yml` prepares the `Validate tune contribution` job for
`pull_request` to `main` on Ubuntu 24.04 with its system Python, GCC and Make. It checks
the trusted base commit, fetches candidate Git objects without checking them out,
and builds only a separately pinned public `chimepond/jottune-synth` commit.
The checkout action uses a full verified revision, persisted credentials are
disabled, and the job has read-only contents permission and no service secrets.
Its reviewed run steps execute the base checker and pinned SDK only; they do
not source candidate scripts or check out candidate files.

The base checker first classifies the pull request. When no commit changes song
data, the job passes with a `Song check not needed` notice and skips the synth
build and the song check; maintainers still review those code, workflow and
documentation changes. Every other pull request runs the full song check.
Failures appear as `Invalid commit identity`, `Song intake closed` or
`Proposal refused` error annotations, and each of these outcomes writes a short
job summary. An eligible proposal whose rendered PCM hash matches an existing
record also gets a `Possible duplicate audio` warning naming that record, and
one whose folded title equals an existing title gets a `Possible title collision`
warning naming those songs; the check still passes. Refusals can quote candidate data, so the checker's log
output is printed with workflow commands stopped and the annotation text is
escaped.

Public automated intake remains closed until a maintainer publishes the trusted
repositories, sets repository variable `JOTTUNE_SYNTH_REF` to the final public
SDK's full 40-character lowercase commit ID, and configures the trusted required
check and review policy. For song proposals, missing, abbreviated or
branch-name SDK references fail before the synth checkout and build. Changes to
checker/workflow code require protected maintainer review; a matching check name alone does not establish trusted code.
GitHub can evaluate a PR's workflow changes, so that protected review policy is
required in addition to this file's data-only validation steps.
Require branches to be up to date before merging so duplicate and append-only
checks use the current trusted catalog.
Do not enable automatic merging or use `pull_request_target` for song proposals.

This workflow has been checked locally, but has not run on GitHub. Before opening
intake, run valid and deliberately rejected data-only PRs on the actual public
repositories and require the reviewed check to pass. Hosted acceptance and
repository settings are explicit release steps.

## Review, acceptance and withdrawal

A maintainer reviews the content and declarations before any merge. Accepted
files keep the same format. The catalog validator accepts the appended entry, and
so does a JotTune Synth exporter with `made_by` support; an older exporter
refuses the entry's `made_by` provenance. A PR merge is separate from ChimePond intake and does not
create a platform receipt or bypass its verification, moderation or grace rules.

A public PR already exposes the submitted bytes and metadata. Request removal
or report a rights issue privately to support@chimepond.com, identifying the
record SHA-256. See [SECURITY.md](SECURITY.md) for private security/rights reporting.
Maintainers can remove current managed files and listings;
Git history, forks, dataset copies, earlier analysis and outside downloads may
remain. Withdrawal cannot promise to erase those copies.

`withdrawn.json` lists withdrawn records so they cannot be proposed again:

```json
{
  "version": 1,
  "records": [
    {
      "record_sha256": "<64 lowercase hex characters>",
      "song_id": "<song ID the record was listed under>",
      "date": "<withdrawal date, YYYY-MM-DD>"
    }
  ]
}
```

A maintainer withdraws a record in one commit: delete `records/<sha256>.tl`,
remove its catalog entry and append one entry with exactly these three fields.
The list holds no reasons, names or report details. Maintainers only append;
they never edit or remove an entry (review policy: the validator checks one
tree, not history). `tools/validate.py` refuses an invalid entry or date, a
duplicate record hash, a listed record still under `records/` and a file that
is not in the canonical two-space JSON form. `tools/check_pr.py` reads the list
from the trusted base and refuses a listed record hash or song ID; a proposal
cannot change the list.
